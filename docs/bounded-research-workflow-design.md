# 有界研究工作流设计

日期：2026-10-24。本文描述当前实现，不代表已经完成真实模型或真实行情的效果验收。

2026-10-25 最新 UI 范围：移除 DeepSeek 发送确认卡、侧栏许可开关和前端许可状态门，首句明确发送直接自动创建会话并请求；不再提供回答后的固定追问按钮，也不再展示“本轮详情 / 参数与执行记录”或内部代码、计数、默认参数、工作流与引用诊断。保留来源、人工行情标记、图表、证据和完整报告。这是前端展示清理，本文中的后端循环、执行器、核验、预算、取消和 API 字段均不变；历史验收记录不代表本次 UI 已完成验收。

## 1. 这次改变了什么

过去的自然研究流程是固定的：理解问题，要求模型提出一次指标分析，计算完成后要求模型回答。模型如果再次请求工具，会被当成异常。

现在保留股票身份和参数核验，但把后续研究改成有限循环：模型看到已有结果后，可以选择继续使用只读工具，也可以结束研究、回答原问题。工具顺序不是写死的，也不要求每轮用完所有工具。

这仍然是一个单股票研究 Agent，不是多个角色辩论，也不是可以自由联网和执行代码的通用 Agent。

```text
用户原问题
  → 理解意图，核对证券目录、日期、来源与指标
  → 歧义需要澄清；范围明确才进入研究
  → 模型选择一个工具
      → 程序核验权限、参数、消息容量和预算
      → 执行只读工具，将结果返回模型
      → 模型选择继续研究，或者提交最终回答
  → 核验请求绑定、指标关系、引用和回答格式
  → 聊天正文 + 可展开主图表、证据和完整报告
```

模型负责“接下来需要了解什么”；程序负责“这个动作是否允许执行、结果是否能支持所引用的事实”。模型提出工具调用，不等于获得执行权限。

## 2. 当前可用的四个工具

| 工具 | 作用 | 重要限制 |
| --- | --- | --- |
| `analyze_daily_indicators` | 获取已确认股票区间的日线，确定性计算原请求指标 | 参数必须与确认请求完全一致；行情读取最多尝试一次 |
| `get_indicator_knowledge` | 查询项目维护的指标定义与计算口径 | 每次选择 1–3 个不同主题；不是搜索互联网或生成新的行情证据 |
| `inspect_research_snapshot` | 查看主快照的来源、范围，或指标可用性 | 必须先有主快照；只读现有结果，不重新取行情 |
| `analyze_additional_indicators` | 在同一批内存日线上补算 1–3 个新指标实例 | 最多一次；不换股票、日期或来源，不重新读取行情 |

例如，模型可以先查询 RSI 的定义，再执行主分析；也可以取得主结果后查看缺项，再补充一个 EMA，最后综合回答。一次主分析已经足够时，应直接结束。

未知工具、批量调用、重复调用 ID、与确认请求不符的股票/日期/来源，都不会因此获得执行权限。相同的已执行工具请求不能通过换一个调用 ID 来重复取数。失败的行情读取也不会自动重试或静默切换供应商。

补充计算不能与原请求重复。对于原请求中已有的指标种类，不能缩短其周期来把“历史不足”变成一个看似可用的信号；当前程序按该种类的已有参数组合核验。

## 3. 为什么分 primary 和 supplement

主分析结果称为 `primary`。它固定绑定原先核验的请求，负责主报告、图表和保存结果。补充计算称为 `supplement`，只补充本轮回答的证据，不能悄悄覆盖主结果。

补充分析不是第二次查询市场。程序从主结果中取出已校验的日线，构建只读内存数据源，再运行同一套确定性指标算法。补充结果沿用主快照的采集时间、真实性标记和复权口径，并使用新的请求 ID。

最终检查要求两个结果的股票、起止日期、来源、复权口径、真实性、采集时间及日线记录完全一致。指标集合可以不同，否则就失去了补算的意义。

每份工具结果的 `f0`、`f1` 等证据别名只在自身结果内有效。因此回答使用：

```text
primary:f7     → 主结果中的 f7 → 对应完整 fact ID
supplement:f7  → 补充结果中的 f7 → 另一个完整 fact ID
```

即使两个别名都叫 `f7`，也不能互相替换。最终正文的引用会转换成完整事实 ID，而不是把两份别名字典混在一起。

补充指标全部历史不足时，仍可保留有效的 primary 回答，但不能引用不存在的补充关系。primary 本身没有可解释指标时，流程不会靠缩短周期或忽略原请求来凑结论。工具视图超过容量时也不会静默删掉部分证据，让模型误认为看到了完整结果。

## 4. 运行预算与容量

研究工作流的单轮上限如下；应用可以传入更紧的限制，模型不能扩大它们。

| 限制 | 当前值 | 含义 |
| --- | --- | --- |
| 模型调用 | 6 次 | 包括前置的意图理解，不是额外再给循环 6 次 |
| 工具调用 | 6 次 | 逐次调用；实际还会先受模型次数约束 |
| 分析尝试 | 2 次 | 主分析与一次内存补算；不是允许两次行情读取 |
| 整轮时间 | 90 秒 | 在协作检查点停止后续调度，不是远端请求硬中断 |
| 已观察 tokens | 24,000 | 根据供应商返回 usage 触发停止，不是提前核算的费用上限 |

这些是同时存在的上限，不是都能用满的配额。例如一个新请求花一次模型调用理解意图，再执行四次“模型选工具→工具返回”，最后一次模型调用回答，就已达到六次模型上限。最后一次模型机会不能再执行工具。

消息协议也有独立容量限制：最多 20 条消息，工具声明加完整消息历史合计最多 20,000 个 ASCII 序列化字符，单个 JSON 对象最多 10,000 个序列化字符。中文经过 JSON 转义后会占用多个 ASCII 字符，不能只按屏幕上看到的字数估算。

每次模型请求前和工具执行边界都会检查消息配对与容量。容量不足时，优先返回有分类的受限结果或停止；不把尚未完成的工具调用留在历史中，也不无限增长上下文。

为让默认八项指标也能完成多步补查，可信请求只在系统消息中传一次，用户原问题单独保留。模型已读取的知识结果随后转换成项目维护的简短定义（保留计算口径与限制），快照检查摘要则指向仍在上下文里的主证据；最新工具结果必须先完整提供给模型。主分析和补充分析的完整证据、别名、工具调用参数及配对始终不删不改。这里不能假设模型记得上一轮的隐藏状态，所以知识摘要不能只写“之前已经告诉过你”。预算结束提示也预先占位，避免最后一轮额外文字把证据挤出容量。更大的组合或长问题仍可能触发上限，最大工具次数不保证所有最大参数组合都能容纳。

还有会话级上限：本地 API 默认每会话最多转发 60 次模型调用、接收 20 条消息；实时 CLI 每次启动保留 15 次模型转发总额、最多 5 条非空问题，分析总上界为 10 次。单轮上限与整次启动上限谁先达到，谁先停止；CLI 不保证五个问题都能使用完整的六次模型预算。

供应商没有返回完整 usage 时，程序不会把未知 token 用量冒充为零费用。取消和截止时间也不能撤回已经发送的远端请求；迟到内容会被丢弃，但可能已经产生供应商费用。

## 5. 最终回答如何生成和检查

模型完成研究后，提交 `research-workflow-response-v1`，不是直接把工具 JSON 显示给用户。协议包括：

- 绑定 primary 的请求 ID、股票代码和实际最新交易日。
- 1–8 条指标关系论断，每条指定 `snapshot`、本地证据别名、关系字段和值。
- 恰好三段正文：`answer` 直接回答问题，`outlook` 给出有条件的方向判断，`watch_for` 说明成立或失效的观察条件。

每段正文 1–600 个字符，必须引用 1–8 个不重复且已经核验的论断；完整最终 JSON 最多 8,000 个字符。提示模型整体用简洁自然的中文，不列出所有指标。除实际指标的标准标签外，正文暂不支持额外阿拉伯数字；精确价格和指标读数保留在数据视图。

程序先按 primary / supplement 分组，复用原有关系验证器：检查完整事实、相邻交易日、单位、依赖、参数和原始精度，并重新计算关系，而不只是判断引用 ID 是否存在。股票、日期、别名空间或关系值不符，整份模型正文都会被拒绝。多余字段、重复 JSON 键、控制字符、NaN、坏引用和不完整结构也不会自动修补成一个成功回答。

兼容的 `research-response-v1` 和 `indicator-explanation-v1` 仍可使用，但只能引用 primary。旧关系协议不会被冒充成新自然语言回答。

**这些检查不能证明自然语言推理正确。** 引用真实关系，仍可能错误解释趋势、忽视冲突或夸大预测。当前验证范围是“请求绑定与指标关系、引用核验”，不是自由文字语义、投资价值、收益预测或胜率验证。禁止额外数字也不能证明中文写出的数量或推论正确。

人工或未经核验的开发 CSV 不用于真实股票方向判断；即使指标算得出来，应用仍会明确说明它是开发数据。没有可用行情或历史不足时，给出简短解释，不把指标清单冒充答案。

## 6. 展示、会话与兼容边界

API 的 `conversation` 负责正文与引用，`research_workflow` 负责有界执行记录。被接受的补充论断会投影为 `supporting_evidence`，包含完整事实 ID、所属请求和程序生成的关系说明；`evidence_snapshots` 用于说明证据来自哪份结果。主图表和原有报告仍绑定 primary，不会因为补算而突然更换指标。

2026-10-25 界面不再把 `research_workflow`、参数、默认值、内部代码和模型/分析计数渲染成回答后的诊断区块，也不逐段展开引用诊断；这些结构化字段仍由后端计算并保留在 API 中，用于核验、兼容和测试。用户按需查看的图表、证据与完整报告仍保留，不能把“移除执行详情”理解为删除证据校验。追问直接输入，不要求固定的 RSI 或 DIF/DEA 快捷按钮。

页面载入和编辑草稿不调用模型；只有用户明确发送，才在需要时创建会话并提交问题。没有额外 DeepSeek 许可卡或勾选步骤，真实模型请求仍可能产生供应商费用。显式重试沿用原编号与幂等保护，不因移除许可门而自动重发或扩展工具权限。

当前会话保存的仍然只有 primary，而不是整轮循环、完整聊天历史或全部辅助证据。后续“查看上次结果”和保存结果追问使用主快照；不能宣称这些追问会记住 supplement。知识解释、证券澄清、条件修改和保存结果追问继续使用各自已有路径，并不强制每个问题都进入研究循环。

取消会清除本轮可展示的新结果；超时或预算停止可以保留停止前已核验的事实，但不会把停止轮次发布为新的会话研究结果。新研究开始时，旧结果不能自动冒充当前结果。API 幂等重放复用已保存的同一请求响应，不重新调用模型或查询行情。

开启方式：

- `ResearchApiService` 默认 `workflow_enabled=True`，网页由这一服务进入新流程。
- 正常的实时 CLI 启动路径传入 `workflow=True`；低层 `run_conversation` 保留旧默认值以兼容原有脚本与测试。
- 低层 `run_natural_research_turn` 保留 `workflow=False` 默认；显式传 `True` 才进入新循环。
- `run_research_turn` 继续是旧显式格式入口，保持两次模型、一次分析的上限。

这不是把全局所有入口悄悄换成新协议，也没有改变数据源必须由可信应用配置的约束。

## 7. 尚未实现的能力

当前没有新闻、公告、财报、基本面、实时行情、网页搜索或选股工具。模型不能因为用户问到这些内容，就假装已经查询过。当前补算也不会自动扩大历史区间、重新取更早行情，或比较第二只股票。

无券商凭据、下单、撤单、交易执行或资金管理接口；所有真实交易仍由人自己操作。日线日期过滤也不等于严格 point-in-time：历史发布时间、修订版本、完整当时可得性仍需未来的数据工程支持。

后续可以在相同边界内增加真正的数据工具，但必须分别实现数据适配、权限、证据与测试，不能只在提示词里列一个不存在的能力。

## 8. 代码位置与验证方法

- `src/trading_companion/research_workflow.py`：有限模型循环、动作顺序、停止与最终答复调度。
- `src/trading_companion/workflow_tools.py`：四个只读工具、授权核验、冻结数据补算和独立观察结果。
- `src/trading_companion/workflow_context.py`：已消费辅助结果的确定性摘要；保留完整主/补充行情证据、用户原文与消息配对。
- `src/trading_companion/workflow_response.py`：多快照回答协议与分组关系核验。
- `src/trading_companion/agent.py`：新旧入口选择、运行预算、结果重验与会话衔接。
- `src/trading_companion/turn_control.py`：单轮预算、取消、截止与实际尝试计数。
- `src/trading_companion/tool_model.py`：工具消息配对、标识符和容量边界。
- `src/trading_companion/api_service.py`、`research_response.py`：公共正文、主图表和辅助证据投影。
- `tests/test_workflow_tools.py`、`tests/test_workflow_response.py`、`tests/test_research_workflow.py`：工具、回答协议与端到端离线集成检查。

集成测试用固定五根人工日线包装成供应商形状，目的是检查应用如何处理该形状的数据，不代表腾讯曾返回这些数据。模型也是预先编排的有限脚本，网络请求与真实密钥读取会被测试保护阻止。

测试覆盖六次模型/四工具/两次计算但仅一次行情读取、提前结束、补充不足、错误股票纠正、跨作用域引用、非法调用、取消、紧预算、上下文超限、主图表/保存绑定及 API 幂等。另有默认八项指标、100根人工日线、三项补算与伪造用户scope文字的回归：完整主/补充视图不变，原问题保留，实际消息容量不超过协议边界。不应从这些测试推断真实模型的理解质量、新闻判断能力、实际数据可用率、真实延迟或投资收益。真实模型和真实行情验收需要单独进行，并明确其调用成本和数据条件。

2026-10-24 历史工作流验收：`scripts/verify.py all`通过1,326项Python测试、428项前端测试、4个Agent场景、90次MVP固定场景及API演练，零跳过；TypeScript检查、生产构建、ASGI实际资源和干净wheel检查通过。当时未做浏览器手动验收，也未新增真实模型或真实行情调用；这些数字不是 2026-10-25 界面清理后的新验收结果，远端CI须以对应Actions运行结果为准。

## 9. 外部架构借鉴

参考的是可解释的架构模式，不是复制代码或照搬整套权限：

- [Dexter](https://github.com/virattt/dexter)：工具结果回到模型后，允许模型有限补查或结束；不是固定一次调用。
- [ValueCell](https://github.com/ValueCell-ai/valuecell)：对话、执行过程和最终展示分开，工具记录不直接充当聊天正文。
- [FinRobot](https://github.com/AI4Finance-Foundation/FinRobot)：确定性计算与模型解释分工，数据和报告有独立接口。
- [TradingAgents](https://github.com/TauricResearch/TradingAgents)：研究能力与综合回答职责分开，但本版没有照搬多角色辩论或自动交易。

我们的实现仍是原有 Python 模块化单体与单个受控研究 Agent。增加真正有用的研究循环，不要求迁移技术栈、引入微服务，或用更多 Agent 名称代替可验证的能力。
